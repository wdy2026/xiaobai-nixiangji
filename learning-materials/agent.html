03 · 先定义它 DEFINITION

两种权威定义

学术定义（ReAct 论文）：Agent 是一种把推理轨迹（Reasoning Traces）与行动轨迹（Action Traces）交错生成的系统，允许语言模型通过行动与外部环境交互，并根据观察结果动态调整推理。[S1]

这一定义强调：推理与行动的耦合。模型不是一次性输出答案，而是在每一步决定"我再想一想"还是"我先查一下"。
工业定义（Anthropic）：在构建有效 Agent 时，Anthropic 把 Agent 定义为"能够动态地指导自身流程和工具使用的系统，具有对任务完成方式的控制权"；与之相对的是 Workflow——人预先写死每一步。[S2]

这一定义强调：控制权归属。Agent 与 Workflow 的关键差别不是用了多少工具，而是循环控制由模型掌握还是由人写死。

一句话个人解释

Agent 是以大语言模型为认知核心，通过循环"推理—行动—观察"调用外部工具以达成目标的自主系统。它不只是"回答"，而是在一个开放环境中"把事情做完"，并且能在执行过程中根据反馈修正路径。

04 · 结构化解释 MECHANISM

核心机制：ReAct 循环

Yao 等人在 2022 年提出的 ReAct 框架首次系统地把"推理轨迹"和"行动轨迹"交错在一个统一的文本序列里。模型在每一步自己决定是继续推理还是调用工具。[S1] 与一次性 Chain-of-Thought 不同，ReAct 允许模型在推理过程中主动修正：如果检索返回为空，它会在下一轮换一种检索策略。

① Reason读任务与历史，决定是否需要工具、用哪个工具
② Act调用一个工具（检索 / 计算 / API）
③ Observe读回结果，更新对世界状态的理解
④ Decide判断目标是否达成；未达成则继续循环
⑤ Answer整合工具结果，给出最终响应

三块组成

  • 大脑（Brain）：LLM 负责规划、推理和决策。它本身只输出文本，不直接改变世界。Wang 等 2023 年的综述把"规划（Planning）"、"记忆（Memory）"、"工具使用（Tool Use）"列为 LLM-based Agent 的三大核心模块。[S3]
  • 工具（Tools）：函数、API、搜索引擎、代码解释器等，让 Agent 获得当前模型权重里不存在的信息或能力。Schick 等 2023 年的 Toolformer 证明语言模型可以自学何时调用工具。[S4]
  • 记忆（Memory）：短期记忆是当前会话的上下文，长期记忆是向量库、数据库或外部摘要。记忆不是上下文本身，而是需要先检索再注入上下文的持久化信息。

Agent 在 AI 工程光谱中的位置

从"单次模型调用"到"完整 Agent"是一个自主性递增的光谱：单次调用没有循环，Workflow 是预先写死的循环，Agent 是模型自己决定何时循环、循环到哪一步。[S2]

最新进展与最佳实践

  • OpenAI Operator（2025）：展示了 Agent 在浏览器环境中通过视觉感知 + 工具调用完成复杂网页任务的路线，强调"计算机使用（Computer Use）"作为工具形态。[S5]
  • Anthropic "Building effective agents"（2024）：提出 Agent 设计的核心经验——先最大化确定性 Workflow，只在确实需要动态决策时才引入 Agent；并强调"护栏（guardrails）"和"回滚"比"更聪明的模型"更重要。[S2]

05 · 应用场景 CASE

场景：学术研究助理 Agent 需要根据用户问题"找到最近 3 年关于长上下文 LLM 的 5 篇高被引论文，并给出方法对比表"。

Agent 怎么解：
  1. Reason：目标需要外部学术数据库，无法凭空编造 → 调用 Google Scholar / Semantic Scholar API。
  2. Act：调用搜索工具 search_papers("long-context LLM", years=3, top=10)。
  3. Observe：得到 10 篇候选论文，含标题、摘要、被引次数。
  4. Reason：需要按被引次数排序并提取方法关键词 → 调用解析工具。
  5. Act：调用 extract_methods(paper_list)。
  6. Answer：生成对比表格，并为每篇给出可信度判断。
边界：Agent 只能基于工具返回的事实回答；如果搜索 API 漏掉重要论文，Agent 不会知道，只能提示"检索结果有限"。因此这类任务需要可验证的工具和明确的成功条件。
来源：类似能力在 ReAct 问答实验[S1]和 Toolformer 工具调用实验[S4]中已被验证；OpenAI Operator 则展示了浏览器 Agent 的工程形态。[S5]

06 · 策略卡片 / 最佳实践 STRATEGIES

以下四条来自 Anthropic 2024 年 Agent 工程最佳实践总结，以及学术界对 Agent 失败模式的分析。

01 · Workflow First

先 Workflow，再 Agent

不要一上来就构建 Agent。先用确定性 Workflow 把任务拆解清楚，只有当步骤无法预先确定、需要模型根据中间结果动态决策时，才引入 Agent。

适用：流程尚不稳定、边界案例多的任务 · 来源 [S2]
02 · Clear Exit

给 Agent 明确的成功条件

Agent 需要知道"什么时候算做完"。没有退出条件的循环会导致预算耗尽或陷入死锁。最佳实践是把成功条件写成可验证的断言。

适用：多步研究、数据收集、代码生成 · 来源 [S2]
03 · Tool Contracts

工具接口要稳定、可验证

Agent 通过工具描述（description + schema）决定调用什么。工具返回必须结构化、可预测，错误信息要明确，否则 Agent 会反复猜测。

适用：所有需要调用 API/函数/数据库的场景 · 来源 [S6]
04 · Human-in-the-Loop

关键动作必须人机确认

对于"下单""转账""发邮件""删除数据"等不可逆或高风险操作，Agent 应暂停并请求人类确认，而不是自动执行。

适用：金融、医疗、运营等高风险领域 · 来源 [S2]

07 · 概念辨析 & 使用边界 BOUNDARY

对比项普通 LLM 调用RAGWorkflowAgent
目标回答单次问题基于检索生成回答完成预先定义的多步流程完成目标，路径由模型决定
循环控制无通常无人写死模型自己决定
工具可选检索工具可选通常必需
失败模式幻觉检索遗漏边界外输入导致崩溃循环死锁、工具错用、累积性错误
最优场景封闭问题知识库问答流程稳定、可枚举目标明确但路径开放
三条硬边界：
  1. 不要把开放性目标交给 Agent："让公司今年活得更好"缺乏明确的完成条件，Agent 会自循环到耗尽预算。
  2. 不要让 Agent 在没有护栏的情况下调用付费/不可逆操作："下单""转账""发邮件"等动作必须有人类确认或回滚机制。
  3. 不要把记忆和上下文混为一谈：上下文是本次推理的输入窗口，记忆是跨会话检索回来的外部信息。

09 · 自测题 QUIZ

  1. （定义） 用一句话区分 Agent 与 Chatbot，并给出判定标准。
    提示判定标准 = 是否能自主决定调用工具并在多步循环中追求目标。
  2. （机制） 解释 ReAct 为什么把"思考"和"行动"放在同一个序列里，而不是先全部推理再全部行动。
    提示因为模型需要根据行动结果（观察）调整下一步推理；分开会失去反馈修正能力。[S1]
  3. （边界） 给出 1 个不该用 Agent 的真实场景，并说明应该用什么替代。
    提示例："把这段中文翻译成英文"用单次 LLM 调用即可；上 Agent 会引入不可控和成本，无收益。
  4. （最佳实践） Anthropic 建议构建 Agent 前先做什么？为什么？
    提示先最大化确定性 Workflow；只有在步骤无法预先确定时才引入 Agent，以降低复杂性和不可控性。[S2]
