概念关系 · Agent / 上下文 / Skill

三件事怎么咬合 — 上下文如何驱动 Agent,Skill 如何沉淀经验

1. 一句话结论 TAKEAWAY

上下文是 Agent 当下"看得到的世界";Agent是带着这个世界去自主行动的实体;Skill是把"哪类任务怎么思考"沉淀成可复用知识包的工程实践。 三者构成一个闭环:Skill 选择 → 加载进上下文 → 驱动 Agent 行为 → 结果再写回上下文 / 记忆库。

4. 互相作用:上下文怎么影响 Agent 的工作? HOW

  1. 窗口决定了 Agent 的"工作记忆上限":超出窗口的历史会被截断或压缩,Agent 立刻"失忆"。[2]
  2. 位置偏差影响 Agent 的判断优先级:Liu 等人 2023 年的"Lost in the Middle"研究实证发现,关键信息放在上下文开头或末尾时召回率最高。[1]
  3. 上下文里的"工具描述"决定了 Agent 会用什么手:不写在上下文里的工具,Agent 无法调用。[5]
  4. 上下文里的"Skill 描述"决定了 Agent 会去选哪个 Skill:description 写不好,Skill 就不会被命中。
  5. 上下文里的检索片段决定了 Agent 是否够事实:没检索就给一句话,Agent 大概率编。[1][3]
个人判断:在工程上,Agent 的失败 80% 来自上下文,而不是 Agent 本身的"智力"。先把上下文做好,再谈模型升级。

5. 互相作用:Skill 如何沉淀可复用的任务知识? WHY

  1. 沉淀的是"路径",不是"答案":Skill 教模型怎么思考、查什么、出什么格式,而不是把答案预写死。
  2. 渐进式披露让它可扩展:每个 Skill 自带 description,模型只读几十 token 就能决定要不要加载主体,避免上下文被冗余填满。
  3. Skill 之间可以组合:arxiv-summarizer + write-as-table 可以叠成"先把论文总结再渲染成图表",这与 Chameleon 等模块化 Agent 的思路一致。[4]
  4. Skill 是把"组织资产"翻译成"模型资产":它把重复任务的标准操作流程(SOP)变成模型可调用的知识。
  5. Skill 的存在让"上下文→Agent"更可控:与其每次在 prompt 里塞一大坨规则,不如把规则封装成 Skill,需要时再调。[6]

6. 一个真实工作的闭环例子 EXAMPLE

用户:"用论文 Lost in the Middle 的方法,帮我看看我们公司那份 PDF 客服报告的问题。"

闭环:
  1. Agent 看到用户消息,从上下文中的 Skill 清单里匹配到 pdf-analyzer + arxiv-reviewer。
  2. 把这两个 Skill 的 SKILL.md 加载进上下文,占约 1.5K token。
  3. RAG 从公司 PDF 检索到 6 段相关文字,塞进上下文。
  4. Agent 进入 ReAct 循环,逐步输出"上下文位置偏差如何影响回答质量"的报告。
  5. 结果写回当前上下文(对话历史),并可选择性写进记忆库,下次问类似问题时优先召回。

7. 易混点 / 反直觉点 MISCONCEPTIONS

  • "上下文越大 Agent 越聪明":错。位置偏差是结构问题,塞太多无关内容会稀释关键指令。[1]
  • "Skill = Prompt":错。Skill 是可按需加载的知识包,Prompt 是常驻上下文。
  • "Agent 自动会用所有 Skill":错。它靠的是description 匹配,写不好就不被选中。
  • "Skill 越多越强":不一定。每个 Skill 都参与 description 抢占,反而互相干扰。
  • "上下文 = 记忆":错。记忆是外部存储 + 按需检索;上下文是本次请求的输入序列。

8. 一句话总结 RECAP

Skill 决定 Agent 会什么,上下文决定 Agent 正在看到什么,Agent 决定 怎么用这两者去把事办成。 好的工程实践 = 写好 Skill 的 description + 管好上下文的信噪比 + 给 Agent 适当的工具与边界。
