大模型的上下文 (Context)

1. 学习目标 OBJECTIVE

  • 描述 "上下文"在 LLM 中的具体含义(不是日常口语里的"语境")。
  • 解释 上下文窗口(Context Window)与位置偏差(Lost-in-the-Middle)对输出的影响。
  • 区分 上下文、记忆、微调、RAG 之间的功能差异。

2. 核心问题 CORE QUESTION

  1. 模型"读到的"和"记住的"是同一回事吗?
  2. 为什么上下文窗口不是越大越好?
  3. 为什么把关键信息塞在上下文开头 / 末尾最有用?
  4. 上下文、记忆、微调、RAG 怎么分工?
  5. 上下文满了之后会发生什么?

3. 结构化解释 STRUCTURED

一句话定义

大模型的"上下文"是指这一次推理请求里,模型能"看见"的全部 token 序列(系统提示 + 用户消息 + 工具结果 + 历史对话 + 检索片段),它决定模型本轮回答的依据。

一个请求的上下文长什么样

System系统提示 / 角色设定
Tools工具描述 + Schema
History历史消息(可能含压缩后摘要)
User + RAG当前问题 + 检索片段
↓
Context Window 所有上述内容被 token 化后送进模型,总长受窗口限制(单位:token,不是字符)。

三件事决定上下文"好不好用"

  1. 窗口大小:决定了能塞多长文档。GPT-4 类早期为 8K,Claude 3 / 4 主流已到 200K,部分模型到 1M+。[2][4]
  2. 位置偏差:"Lost in the Middle" 论文实证发现,模型对开头和结尾的信息召回最强,中间段最弱。[3]
  3. 信噪比:塞太多无关内容会稀释关键指令,模型会"分心"。

4. 应用场景 CASE

场景:客服让 AI 助手参考一份 80 页 PDF 回答客户问题。

怎么用上下文:
  1. 把 PDF 拆成 chunk(每 500 token 一段),用嵌入模型建索引。
  2. 用户提问时,先检索最相关的 3–5 个 chunk。
  3. 把"系统提示 + 历史 + 检索片段 + 用户问题"拼成完整上下文送给模型。
  4. 回答时附引用页码,便于用户追溯。
边界:如果检索不准,再大的窗口也救不了答案;同时也不要把整本 PDF 原样灌进上下文 —— 会触发"中间遗忘"并严重拖累成本。

5. 概念辨析 & 使用边界 BOUNDARY

概念持久性更新成本能学到新事实吗
上下文仅本次请求每次请求重算能(写进 prompt)
记忆(Memory)跨会话中等(写向量库)能
微调(Fine-tune)永久(进权重)高(重新训练)能,但昂贵
RAG由检索条件决定低(只需更新文档库)能,最便宜
四条硬边界:
  1. 不要把"敏感信息"放进上下文:它会被发往第三方 API,日志可能被留档。
  2. 不要假定"窗口大 = 记得住":位置偏差是结构问题,与大小无关。
  3. 不要混淆"上下文里的事实"和"模型学到的":前者只对本次推理有效,后者是权重。
  4. 不要在上下文里塞"几乎用不到的旧消息":每多一个 token 都是钱,且会冲淡当前指令。

6. 自测题 QUIZ

  1. (定义) 用一句话区分"上下文"和"记忆",并给出存储位置的差异。
    提示 上下文存在本次请求的 prompt里;记忆存在外部存储(向量库 / 数据库),需要时再检索回上下文。
  2. (机制) 解释"Lost in the Middle"现象为什么会发生,以及它对"提示词排版"的实操影响。
    提示 因为 attention 分布与位置相关;实操 = 把最重要指令放最开头或最末尾,关键引用放结尾 System 提示里。
  3. (边界) 假设你有一个 200K 窗口的模型,要把三本 PDF 给它当知识库,你会怎么设计?为什么不直接整本灌进去?
    提示 用 RAG:先建索引,提问时只检索相关片段拼成上下文。直接灌 → 中间遗忘 + 成本爆炸 + 单次会话难以追溯引用。
