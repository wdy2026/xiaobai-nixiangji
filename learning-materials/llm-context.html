1. 学习目标 OBJECTIVE

  • 描述 "上下文"在 LLM 中的具体含义,区分它与日常语境中"上下文"的差异。
  • 解释 上下文窗口(Context Window)、位置偏差(Lost-in-the-Middle)和稀疏/线性注意力机制如何共同决定模型的长文本处理能力。
  • 区分 上下文、记忆(Memory)、微调(Fine-tune)和 RAG 在长文本任务中的分工。

2. 核心问题 CORE QUESTION

  1. 模型"看到的"和"记住的"是同一回事吗?
  2. Transformer 的自注意力为什么让上下文窗口成为计算瓶颈?
  3. 为什么上下文窗口不是越大越好?
  4. 为什么把关键信息放在上下文开头或末尾,模型更容易记住?
  5. 上下文满了之后会发生什么?

3. 结构化解释 STRUCTURED

一句话定义

大模型的"上下文"是指当前推理请求中,模型能"看见"并用于生成下一个 token 的全部输入序列,包括系统提示、历史对话、检索片段和工具返回。它不等同于"记忆",也不等同于"知识"。[1][3]

一个请求的上下文长什么样

System系统提示 / 角色设定
Tools工具描述 + Schema
History历史消息(可能含摘要)
User + RAG当前问题 + 检索片段
↓
Context Window 所有 token 拼接后送进模型,总长度受窗口限制(单位是 token,不是字符)。

核心机制:从 Attention 到上下文窗口

  1. 自注意力的二次复杂度:Transformer 中每个 token 都要和序列中所有其他 token 计算注意力,序列长度为 n 时计算量和显存都是 O(n²)。[1] 这直接限制了上下文窗口的大小。
  2. 长上下文模型有两条路线:
    • 路线 A:稀疏/局部注意力。Longformer 用滑动窗口 + 全局注意力,把复杂度降到 O(n)。[2]
    • 路线 B:序列并行 + 分块。Ring Attention 把长序列切到多个设备上计算,让窗口可以扩展到百万 token。[4]
  3. Infini-attention 等压缩记忆:在固定内存里压缩历史上下文,使模型能处理"无限"长输入,但会引入信息损失。[5]

位置偏差:为什么开头和末尾最有效

Liu 等人 2023 年的论文"Lost in the Middle"对多个长上下文模型做了系统评测,发现:当关键信息放在文档开头或末尾时召回率最高;放在中间时,即使模型标称支持长上下文,性能也会显著下降。[3] 这不是窗口大小能解决的问题,而是注意力分布和训练数据偏差导致的结构性问题。

上下文与相邻概念的分工

上下文是当前推理的输入;记忆(Memory)是跨会话保存并检索的外部信息;RAG 是把外部文档按需切片送入上下文的技术;微调(Fine-tune)则是把知识固化到模型权重里。[6][7]

4. 应用场景 CASE

场景:法律助理需要在一份 200 页的合同里找出"所有关于违约责任的条款,并判断是否包含仲裁约定"。

怎么用上下文:
  1. 如果模型窗口只有 4K token,无法一次性塞进整份合同 → 需要先用 RAG 或分段检索。
  2. 把合同拆成条款级 chunk,用嵌入模型建索引;对查询"违约责任 + 仲裁"检索最相关的 5 个 chunk。
  3. 把"系统提示 + 检索到的 chunk + 用户问题"拼成上下文送给模型。
  4. 模型基于上下文中的证据回答,并标注引用来源。
边界:如果检索遗漏了关键条款,再大的窗口也救不了答案。同时,如果 chunk 切分破坏了跨段语义,模型可能看不出上下文关联。
来源:类似的法律/金融长文本分析任务在 Lost in the Middle 研究[3]和 Anthropic 100K 上下文应用案例[6]中均有讨论。

5. 概念辨析 & 使用边界 BOUNDARY

概念持久性更新成本适用场景
上下文仅本次请求每次请求重算当前对话、一次性长文档
记忆(Memory)跨会话中等(写向量库)长期用户画像、跨任务经验
微调(Fine-tune)永久(进权重)高(重新训练)领域专用语言、固定知识
RAG由检索条件决定低(只需更新文档库)动态知识库、可溯源问答
四条硬边界:
  1. 不要把"敏感信息"放进第三方 API 的上下文:它会随请求离开本地,日志可能被留档。
  2. 不要假定"窗口大 = 记得住":Lost in the Middle 是结构性问题,与窗口大小无关。[3]
  3. 不要把上下文塞满无关的旧消息:每多一个 token 都是计算和费用,还会冲淡当前指令。
  4. 不要把记忆当成上下文:长期记忆需要先检索再写入上下文,否则模型本轮根本看不到。[7]

6. 自测题 QUIZ

  1. (定义) 用一句话区分"上下文"和"记忆",并指出它们分别存在哪里。
    提示上下文存在本次请求的 prompt 里;记忆存在外部存储,需要时通过检索注入上下文。
  2. (机制) 解释为什么 Transformer 自注意力会限制上下文窗口,以及 Longformer 如何缓解这个问题。
    提示自注意力是 O(n²);Longformer 用稀疏注意力把复杂度降到 O(n),牺牲全局交互换取长度。[1][2]
  3. (边界) 假设你有一个 200K 窗口的模型,要把三本 PDF 当知识库,你会怎么设计?为什么不直接整本灌进去?
    提示用 RAG 检索片段再拼上下文。直接灌 → 中间遗忘 + 成本爆炸 + 难追溯引用。
