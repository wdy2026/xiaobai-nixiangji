Skill · 可复用的任务知识包

1. 学习目标 OBJECTIVE

  • 描述 Skill 在 AI Agent 系统里扮演什么角色,与 Prompt / Tool / Agent 的区别。
  • 解释 SKILL.md 的典型结构(YAML frontmatter + 说明 + 可选脚本/资源)。
  • 应用 判断一个工作流该写 Skill 还是只写一段 Prompt。

2. 核心问题 CORE QUESTION

  1. Skill 和一段写进 System Prompt 的指令有什么不同?
  2. Skill 是不是就是 OpenAI 的 GPTs / Assistants?
  3. Skill 为什么通常做成"按需加载",而不是一次塞进上下文?
  4. Skill 写完放在哪?谁负责加载它?
  5. Skill 的可复用性和 Agent 的自主性会不会冲突?

3. 结构化解释 STRUCTURED

一句话定义

Skill 是 把特定任务的专业知识(指令、流程、参考资料、可选脚本)打包成一个名字清楚、可被按需加载的文件夹,让 AI 在需要时"临时学会"做这一件事。

SKILL.md 的三段式结构

① 元数据YAML 写在文件最上方:name / description / 触发场景说明
② 行为说明Markdown 主体:适用场景、输入、流程、输出、自检
③ 资源附件scripts / templates / reference.md 等按需加载

"渐进式披露"是如何工作的

  1. 系统启动时,模型只看到每个 Skill 的 name + description(几十 token)。
  2. 用户提出任务 → 模型判断哪个 Skill 匹配 → 读取其 SKILL.md 全文。
  3. 如果 SKILL.md 里引了脚本或模板,需要时再读相应文件。
  4. 整个过程类似"工具调用",但载的是知识而不是外部 API 结果。

Anthropic 在 2025 年公开的 Agent Skills 即采用这种"先读 description,再加载主体"的范式,目的是不污染上下文的同时让专长可复用。[1][2]

4. 应用场景 CASE

场景:你每次让 AI 总结 arXiv 论文都要重复一段很长的固定指令 + 输出格式,你把它打包成 arxiv-summarizer Skill。

怎么落地:
  1. 建 arxiv-summarizer/SKILL.md,YAML 描述"用结构化方式总结学术论文"。
  2. 正文写明:输入是论文标题 / 摘要 / PDF 链接,输出固定为3 句话核心 + 1 张方法表 + 1 段质疑。
  3. 附一个 templates/summary-table.md 给模型参考。
  4. 以后每次只要说"用 arxiv-summarizer 处理这篇",模型就知道怎么做。
边界:如果任务本身不重复(Skill 写完只用一次),就不值得做 Skill,Prompt 反而更快。

5. 概念辨析 & 使用边界 BOUNDARY

对比项PromptSkillTool / FunctionAgent
形态一段文本带元数据的文件夹可执行函数带循环的运行实体
复用方式复制粘贴按需加载按需调用—
能写代码否是(可选)必须通常包括
核心价值风格控制专长沉淀能力扩展目标完成
三条硬边界:
  1. 不要把 Skill 当万能钥匙:它沉淀的是我每次都要做的事,不是"任何事都能做的开关"。
  2. 不要把"业务规则"塞进 description 里全部公开:description 永远加载 → 写得越短越隐私友好。
  3. 不要和"工具调用"混淆:Skill 是告诉 AI 怎么做事,Tool 是让 AI 真的去拿数据 / 改状态。

6. 自测题 QUIZ

  1. (定义) 用一句话区分 Skill 与 System Prompt。
    提示 System Prompt 永久占用上下文;Skill 是按需加载的知识包,不调用就不占位置。
  2. (机制) 解释 SKILL.md 里为什么要单独留一段"输入字段表",而不是直接把字段写进 description。
    提示 description 每轮都加载,要短;详细信息按需加载,可以长。渐进式披露的关键。
  3. (边界) 给你一个"每天打开电脑,自动把昨天下载文件夹的文件按类型归档"的需求,你会不会写成 Skill?为什么?
    提示 这更像是 自动化脚本 + 定时任务,不是可被 AI 调用、依赖 AI 推理的"知识包"。Skill 强调AI 判断 + 知识沉淀,归档更适合作 automation。
