Skill · 可复用的任务知识包

03 · 先定义它 DEFINITION

两种权威定义

工业定义（Anthropic）：Agent Skills 是"可复用的能力模块"，让 Agent 在运行时根据任务需求加载特定的指令、工具配置和上下文模板，从而扩展其专业能力，而不把所有规则都塞进系统提示。[S1]

这一定义强调：模块化与按需加载。Skill 把专长拆出来，需要时再读。
工程定义（OpenAI）：Function Calling 让模型能够根据用户输入自动选择并调用外部函数；而 Skill / GPTs 则是在这一能力之上，把"何时调用、怎么调用、输出什么格式"的完整知识打包成一个可复用单元。[S2]

这一定义强调：Skill 是 Tool Learning 的工程封装。它不是单个函数，而是围绕函数的知识包。

一句话个人解释

Skill 是 把特定任务的专业知识（指令、流程、参考资料、可选脚本）打包成一个名字清楚、可被按需加载的模块，让 AI 在需要时"临时学会"做这一件事，而不是把规则永久塞进上下文。

04 · 结构化解释 MECHANISM

SKILL.md 的三段式结构

① 元数据

YAML 写在文件最上方：name / description / 触发场景说明。description 是 Skill 的"名片"，模型靠它判断要不要加载。

② 行为说明

Markdown 主体：适用场景、输入字段、执行流程、输出结构、自检清单。这是 Skill 的"说明书"。

③ 资源附件

scripts / templates / reference.md 等按需加载。需要时再读，不常驻上下文。

"渐进式披露"与上下文节省

  1. 系统启动时，模型只看到每个 Skill 的 name + description（几十 token）。
  2. 用户提出任务 → 模型判断哪个 Skill 匹配 → 读取其 SKILL.md 全文。
  3. 如果 SKILL.md 里引了脚本或模板，需要时再读相应文件。
  4. 整个过程类似"工具调用"，但载的是知识而不是外部 API 结果。

这种设计与 Chameleon 等模块化 Agent 的思路一致：不要把所有能力一开始就拼进 prompt，而是让模型在运行时根据任务动态组合模块。[S3]

学术脉络：从 Tool Use 到 Skill 封装

Skill 并非凭空出现。它的底层是工具学习（Tool Learning）研究：Toolformer 证明 LLM 可以自学何时调用工具；Gorilla 证明模型可以学会调用海量 API；Chameleon 证明模型可以按任务组合不同工具。[S4][S5][S3] Skill 是这些能力在工程层面的封装形态 —— 把"调用什么、怎么调用、输出什么格式"写成可复用的知识包。

05 · 应用场景 CASE

场景：研究团队每次让 AI 总结 arXiv 论文都要重复一段固定指令 + 输出格式，于是打包成 arxiv-summarizer Skill。

怎么落地：
  1. 建 arxiv-summarizer/SKILL.md，YAML 描述"用结构化方式总结学术论文"。
  2. 正文写明：输入是论文标题 / 摘要 / PDF 链接，输出固定为3 句话核心 + 1 张方法表 + 1 段质疑。
  3. 附一个 templates/summary-table.md 给模型参考。
  4. 以后每次只要说"用 arxiv-summarizer 处理这篇"，模型就知道如何调用工具、解析 PDF、整理格式。
边界：如果任务本身不重复（Skill 写完只用一次），就不值得做 Skill，Prompt 反而更快。
来源：类似的可复用指令封装在 Anthropic Agent Skills 文档[S1]和 OpenAI Function Calling 指南[S2]中均有工程化描述。

06 · 策略卡片 / 最佳实践 STRATEGIES

01 · SHORT DESCRIPTION

description 要短而准

description 是 Skill 的"名片"，模型每轮都会看。如果写得太长，会浪费上下文；如果写得不准，Skill 永远不会被命中。

适合：所有 Skill · 来源 [S1]
02 · INPUT CONTRACT

明确定义输入字段

把必填/选填字段、格式、示例写清楚。模糊的输入会让模型在调用时猜，降低成功率。

适合：需要复杂参数的任务 · 来源 [S2]
03 · SELF-CHECK

包含自检清单

在 SKILL.md 末尾列出交付前必须检查的事项。这能显著降低 AI 幻觉和输出格式错误。

适合：对准确性要求高的任务 · 来源 [S6]
04 · VERSIONING

用 Git 管理 Skill 版本

Skill 也是会迭代的。把 SKILL.md 放在版本控制里，改动可追溯，也能回滚到稳定版本。

适合：长期维护的项目级 Skill · 来源 [S6]

07 · 概念辨析 & 使用边界 BOUNDARY

对比项PromptSkillTool / FunctionAgent
形态一段文本带元数据的文件夹可执行函数带循环的运行实体
加载方式常驻上下文按需加载按需调用自主运行
能写代码否是（可选）必须通常包括
核心价值风格/任务控制专长沉淀能力扩展目标完成
四条硬边界：
  1. 不要把 Skill 当万能钥匙：它沉淀的是"我每次都要做的事"，不是"任何事都能做的开关"。
  2. 不要把业务规则全塞进 description：description 永远加载，应保持简短；详细规则放在 SKILL.md 主体里按需读取。
  3. 不要把 Skill 和 Tool 混淆：Skill 是告诉 AI 怎么做事，Tool 是让 AI 真的去拿数据 / 改状态。[S4][S2]
  4. 不要把一次性任务做成 Skill：建 Skill、维护 description 都有成本，只在重复任务上才划算。

09 · 自测题 QUIZ

  1. （定义） 用一句话区分 Skill 与 System Prompt。
    提示System Prompt 永久占用上下文；Skill 是按需加载的知识包，不调用就不占位置。
  2. （机制） 解释 SKILL.md 里为什么要单独留一段"输入字段表"，而不是直接把字段写进 description。
    提示description 每轮都加载要短；输入字段表属于详细规则，按需加载可以长。这是渐进式披露的关键。
  3. （边界） 假设需求是"每天打开电脑，自动把昨天下载文件夹的文件按类型归档"，你会不会写成 Skill？为什么？
    提示不会。这更像自动化脚本 + 定时任务，不是依赖 AI 推理的"知识包"。Skill 强调 AI 判断 + 知识沉淀。
  4. （学术脉络） Toolformer、Gorilla、Chameleon 三篇论文分别解决了 Skill 形成的哪个前置问题？
    提示Toolformer：自学何时调用工具；Gorilla：学会调用海量 API；Chameleon：按任务组合工具。三者共同支撑了 Skill 的模块化封装。[S3][S4][S5]
